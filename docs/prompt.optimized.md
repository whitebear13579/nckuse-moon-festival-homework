# 專案任務：中秋節主題・像素風互動式網頁應用

## 1. 角色與目標

你是一名資深全端開發工程師。請從零開始設計並開發一個**以「中秋節」為主題的互動式網頁應用程式**，視覺以**像素風（Pixel Art）**為核心，動畫效果與整體 UI/UX 必須美觀、流暢。

交付順序：**規劃（撰寫 `docs/SPEC.md`）→ 實作 → 測試 → 審查**，詳見第 9 節。

## 2. 哪些已固定、哪些由你決定

**已固定（不可更動）**

| 項目 | 要求 |
| --- | --- |
| 主題 | 中秋節 |
| 技術棧 | Next.js 16 + Tailwind CSS + TypeScript |
| 視覺風格 | 像素風（Pixel Art） |
| 規格文件 | 完整的 `docs/SPEC.md`（內容要求見第 8 節） |
| 測試 | 必須規劃並實作（要求見第 7 節） |

**由你自行評估與決定**（並將理由記錄於 `SPEC.md`）

- 產品構想與內容
- 是否需要後端，以及後端方案
- 動畫方案、第三方套件、整體架構與其餘技術選型

遇到需求不明確時，請自行做出合理判斷，並把假設寫進 `SPEC.md`，不需中斷詢問。

## 3. 產品構想

題材不限，越有趣、越有創意越好。以下僅為靈感，不必侷限：

中秋賀卡、月餅 Clicker、烤肉模擬器、月相模擬、互動故事，或任何你覺得有趣的東西。

請只選定**一個**構想並做到完整，並在 `SPEC.md` 說明：

- 一句話概念
- 目標使用者與使用情境
- 核心互動迴圈（使用者做什麼 → 系統如何回饋 → 為什麼會想繼續玩）
- 為什麼選這個構想（有趣程度、適合像素風、範圍可控、能展現動畫品質）

## 4. 技術與架構

**技術棧**：Next.js 16 + Tailwind CSS + TypeScript。Next.js 16 較新，實作前請先用 Context7 查最新文件，不要僅憑記憶撰寫。

**後端評估**：請自行判斷構想是否需要後端。可選方案包含 Supabase、Firebase 等現成服務，或要求我用自己的主機自建後端。

- 評估標準只看兩件事：**從開發到部署、CI/CD 的可維護性**，以及**可擴展性**。
- **不需要**考慮我額外付出的人力或操作成本。
- 請在 `SPEC.md` 以「決策紀錄」形式寫明：最終方案、比較過的替代方案、取捨理由。
- 若判斷不需要後端，也請說明理由。
- 若需要我自行架設，請提供完整的架設步驟與所需環境變數。

## 5. 視覺與體驗要求

- **像素風要貫徹到底**：包含字體、配色（有限色盤）、UI 元件、圖示、動畫，以及像素化縮放（如 `image-rendering: pixelated`）。
- **動畫品質**：過場與互動都要流暢自然，動畫優先使用 `transform` / `opacity`；並提供 `prefers-reduced-motion` 的降級方案。
- **素材與效能**：圖片體積大，會拖慢載入。請優先用程式繪製或 sprite 的像素素材（CSS、SVG、Canvas 等）。若使用 [Unsplash](https://unsplash.com/) 圖片，請壓縮、最佳化並延遲載入，且只用在確有必要處。
- **中文字體**：可使用 [emfont](https://font.emtech.cc/docs)（免費中文 Webfont 服務），請挑選符合像素風的字體，並注意載入效能。

## 7. 測試要求

請規劃並撰寫完整測試（含單元測試與整合測試），確保上線前所有功能都被正確驗證。測試至少涵蓋：

| 類別 | 應驗證的重點 |
| --- | --- |
| 狀態轉換 | 合法轉換的結果、非法轉換被拒絕或忽略、邊界狀態 |
| localStorage | 正常讀寫、資料不存在、資料損壞、版本遷移、儲存空間不可用 |
| API | 成功、失敗、逾時、回應格式錯誤（若有後端則含 Route Handler / Server Action） |
| validation | 合法輸入、非法輸入、邊界值 |
| 其他 | 依專案需要補充（如計時器與遊戲迴圈、隨機性、元件互動等） |

**品質準則**

- 不要寫沒有實際意義的測試來湊數（例如空泛的 snapshot、只驗證常數、只驗證 mock 本身）。
- 每個測試都應對應到某條 Acceptance Criteria 或某個具體風險。
- 測試須為確定性的：計時用 fake timers，隨機用可注入的 seed。
- 測試工具由你選擇，需能以單一指令執行，並可在 CI 中跑。

## 8. `docs/SPEC.md` 內容要求

請在 `docs/` 資料夾撰寫完整的 `SPEC.md`。

**必要章節**

1. **要做什麼**：產品概述與構想說明（見第 3 節）
2. **主要功能**：功能清單，並標示優先順序
3. **系統行為**：狀態機、資料流、邊界情況與錯誤處理
4. **Acceptance Criteria**：每一條都必須可驗證（建議用 Given / When / Then 或勾選清單），並標明對應的測試
5. **Non-goals**：明確列出這次不做的事

**其他請一併補充**（即原需求中的「and any other」）

- 技術選型與架構決策（含後端決策紀錄與套件取捨）
- 資料模型與 API 設計（若有後端）
- 像素風設計系統：色票、字體、元件、動畫規範
- 效能預算與無障礙考量
- 測試計畫（對應第 7 節）
- 專案目錄結構
- 部署與 CI/CD 流程
- 實作里程碑與任務拆解
- 風險與未決事項

## 9. 執行流程

1. **規劃**：確認構想，用 Context7 查閱所需文件，完成 `docs/SPEC.md`。
2. **實作**：依 `SPEC.md` 開發，並依需求使用相關 skills。
3. **測試**：補齊並執行第 7 節的測試，確保全數通過。
4. **審計與修正**：建議用 `fuck my shit mountain` 做一次工程審計，修正高優先級問題並補上回歸測試。
